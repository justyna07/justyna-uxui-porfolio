ContextFluent, fast, and sometimes wrong

The first version was a pipeline, not a product: a scheduled job pulled last week's Google Ads and GA4 numbers, handed them to a model with a prompt, and dropped a draft email in the account manager's inbox. It saved time immediately. Then an account manager noticed a draft that said organic traffic had risen, in a report that only had paid data in it. The model had filled a gap with something plausible.

Nobody had sent a wrong claim to a client, but nobody could prove they hadn't, either. Managers started re-reading every draft against the dashboard, which took longer than writing it themselves.

I shadowed three account managers writing reports by hand. Their process was the same every time: look at four numbers, look for anything unusual, explain the unusual thing in a sentence, say what happens next. The model could do all four steps. What it couldn't do was know when it was making something up, and the interface gave the manager no way to tell either.

Problem statement

Account managers cannot trust or efficiently review automated report drafts because the draft gives no way to trace a sentence back to the data it came from, so every draft is re-verified from scratch or sent on faith.

Metrics: minutes per report, share of drafts edited before approval, unsupported claims caught before send, unsupported claims sent (target zero).

ConstraintA client-facing email can't be 95% right

  • Zero tolerance for invented numbers. A wrong figure in a client email is a trust problem, not a typo. The design had to make an unsupported claim impossible to send, not just unlikely.
  • Partial data is common. GA4 exports lag, call-tracking APIs rate-limit, a client disconnects a property. The pipeline had to know the difference between "nothing happened" and "we couldn't see."
  • Managers edit everything. Every manager rewrote the draft in their own voice. The tool had to treat editing as the normal path, not a failure of the model.
  • Accountability. If a client asked "who wrote this," the answer had to be a person's name, with a record of what the model drafted and what the person changed.

DecisionCheck every numeric claim against its source, and block sending until the check passes

The patterns, and the reason for each

  • Data before draft. The KPI strip and the anomaly list render first, with the source named on each anomaly. The manager sees the facts before reading the model's sentences about them.
  • Claim checking, not just citations. Each numeric claim is matched to the metric that produced it. A claim with no metric behind it is marked unsupported and names what's missing ("GA4 organic data is not in this pipeline").
  • Gated approval. One unsupported claim disables Approve. The manager can't skim past a red mark; they have to edit it out and re-check.
  • Editing is the default path. The draft is a textarea, not a preview. The tool records how much was changed, which turns "managers rewrite everything" from an anecdote into a metric for improving the prompt.
  • Refuse on partial data. If a source returns nothing, no draft is written. A report drafted from half the data would read as confidently as a complete one, which is the worst failure mode.
  • Approve and send are different buttons. Approval is a judgement about the content; sending is an action with a recipient. Splitting them produced zero accidental sends in the pilot and gave the log a clean "approved by" entry.

Trade-offScope the model down to make the product trustworthy

The first prompt let the model interpret freely. The shipped version gives it a fixed structure (greeting, four numbers, anomalies from a list the pipeline computed, one next step) and only the data in the pull. It writes less interesting prose. It also stopped inventing context, because there was no gap to fill.

Engineering pushbackMatching claims to metrics by pattern is brittle; the developer wanted the model to emit structured JSON with each sentence tagged to its source. We did both: structured output from the model, plus an independent regex check on the final text after the manager's edits, because the manager can introduce a wrong number too.

The other trade-off: anomaly detection is a simple four-week comparison with thresholds, not a model. It misses subtle things. It also never flags something that isn't there, which for a client-facing tool mattered more.

The claim-check pattern was reused in the search term tool's export step, and the "refuse on partial data" rule became a standard in the team's automation guidelines.

ReflectionWhat I'd do differently

  • The edit-rate metric told me the prompt needed work, but not how. Next time I'd capture the manager's edits as structured feedback (tone, missing context, wrong emphasis) so the prompt improves from real corrections.
  • Clients never saw the tool, and I never asked them whether the new reports were clearer. The outcome section should have a client-side measure, not just a manager-side one.
  • I built the first version as a pipeline and bolted the interface on. Starting from the manager's review flow would have led to the claim checker in week one instead of week three.
